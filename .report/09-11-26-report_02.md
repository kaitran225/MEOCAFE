# Database logic review — POS.Data (SQLite / DbUp)

Reviewed the whole data layer: schema migrations (V1–V15), the migration runner, connection/path/ensure logic, and all 18 repositories, cross-checked against the live `data/hienxanh.db`. Method: code-level read of `POS.Data` + `POS.Core`, live schema/`SchemaVersions` inspection via sqlite, git history across `Migrations/` and `data/`, and an empirical fresh-DB migration simulation. I did not launch the app.

## P0 — schema drift: migrations V4 & V5 were deleted, and the app only works by accident

The live DB's `SchemaVersions` journal records `V4__Orders_kitchen_status.sql` and `V5__Customer_and_order_customer.sql` as **applied**, but those files do not exist in `POS.Data/Migrations/` nor in **any** git commit (`git log --all --name-status`). The columns they used to add are still in the live DB but are created by **no** committed migration:

- `orders.kitchen_status`, `orders.customer_id` — live only
- `customer.email`, `customer.address` — live only (V1's `customer` has just name/phone/point)

Yet the code depends on them: `OrderRepository.cs` (SELECT/INSERT/UPDATE on `kitchen_status`, `customer_id`; lines 19, 31, 43, 56, 74, 96), `CustomerRepository.cs` (`email`, `address`; lines 19, 30, 42, 55, 72, 85), `V10__Seed_demo_drinks.sql:28` (`INSERT INTO orders (... kitchen_status ...)`), and the `Order` / `Customer` models.

Why it still works: `data/hienxanh.db` is **git-tracked**, and `DatabasePathResolver` walks up from the output dir to find that existing file — so dev builds inherit a pre-migrated DB that happens to have the columns.

A fresh database is broken (reproduced — I applied the committed migrations in numeric order to a new file):

```
OK   V1..V9
FAIL V10__Seed_demo_drinks.sql -> table orders has no column named kitchen_status
OrderRepository    SELECT -> no such column: customer_id
CustomerRepository SELECT -> no such column: email
```

So any machine that doesn't get the committed `.db` fails at startup with the "Không khởi tạo được cơ sở dữ liệu" dialog.

**Fix:** (1) recreate `V4__Orders_kitchen_status.sql` / `V5__Customer_and_order_customer.sql` with the exact filenames so DbUp re-runs them only on fresh DBs (shipped DB already has them journalled → skipped). (2) Add a V16 guard (`PRAGMA table_info` checks → `ALTER TABLE`) so DBs created in the gap heal themselves. (3) Remove V10's `kitchen_status` dependency (or add the column inline in V10 before the demo insert).

## P1 — binary DB committed to git is the de-facto schema source of truth

`data/hienxanh.db` is tracked; WAL/SHM are ignored, and `DatabaseSyncService.CheckpointForGitSync()` exists to make the file git-friendly. But **WAL is never enabled** — no `PRAGMA journal_mode=WAL` anywhere, and the live DB reports `journal_mode: delete`. So `DatabaseCheckpoint.WalCheckpointTruncate` (`DatabaseEnsurer.cs:14`) is a silent no-op. Consequences: schema can't be reproduced from source, teammates get divergent DB state, and the sync-on-save flow is fiction. Recommend gitignoring the `.db`, treating migrations (+ V14 menu seed) as the single source of truth, and deleting the checkpoint no-op or actually enabling WAL if the file-sync workflow is kept.

## P1 — migration ordering is implicit, and filename order is wrong

`DatabaseMigrationRunner.cs` pulls `Directory.GetFiles` (arbitrary order) and encodes the version only as `RunGroupOrder`. DbUp re-sorts by that, which saved it — lexical filename order is actively wrong: `V10__…` < `V1__…` (< `'0'` < `'_'`); my first (lexical) simulation failed instantly on "no such table: categories". Make it deterministic: sort scripts by parsed version before handing them to DbUp (or validate contiguity).

## P2 — inconsistent timezone handling around stored-UTC timestamps

`created_at` / `start_at` are stored as **UTC** (`CURRENT_TIMESTAMP`, `datetime('now')`), but filters mix local and UTC: `AnalyticsRepository.cs:18,28` use `'now','localtime'`, `:51` compares UTC stored dates against local `@Start/@End`, while `:81` uses plain `'now'` (inconsistent with its month/year siblings). `ShiftSessionRepository.cs:59` `date(start_at) = date(@Day)` compares a UTC date to a **local** day string → shifts/orders near midnight land on the wrong day for any non-UTC timezone. Pick one convention (store localtime, or keep UTC and convert all comparisons) and apply it everywhere — "today's sales" and "shift of the day" are core POS queries.

## P2 — analytics week series is sparse

`GetTotalSaleByWeekAsync` (`AnalyticsRepository.cs:45`) returns one row per day-with-sales, not 7 zero-padded days. Any chart expecting a fixed week (Mon–Sun) will draw gaps. Zero-fill the window.

## P2 — IEmployeeRepository is declared but never implemented

Contract + `employee` table + `Employee` model exist, but there's no `EmployeeRepository` anywhere in the codebase (and it's never referenced). Either the feature is unfinished (then it needs an implementation to register) or the contract is dead code to remove. Also note V2 seeds no default admin (by design).

## Minor / non-blocking

- `RefundRepository.cs:35` and `AuditLogRepository.cs:53` call `GetDateTime` on `TEXT` columns while the rest of the codebase uses the `ReadDateTime` helper (works because SQLite's ISO format parses, but inconsistent).
- `Order.cs` has `Percentage` / `GrandTotal` that no repository ever reads or writes.

## Worth keeping

Repository code is uniform and correct: every query is parameterized, mapped directly to models, and the `ReadDateTime` / `GetBooleanCompat` helpers paper over SQLite type quirks cleanly. `Category`/`Table`/`Shift`/`Recipe` repos all match their live schema. The migration-as-batch-of-files pattern with `WithTransactionPerScript()` is the right shape — it's just missing two files.

**My fix order:** (1) restore V4/V5 + V16 guard so a fresh DB boots and orders/customer queries pass, (2) drop the committed `.db` and enable WAL or kill the checkpoint no-op, (3) explicit migration ordering, (4) unify the timezone convention, (5) zero-fill the weekly series and decide on `IEmployeeRepository`.
